= kodein-github-actions
:toc: macro
:toclevels: 2
:idprefix:
:source-highlighter: highlight.js

*GitHub Actions for Kodein projects, written in Kotlin/JS.*

kodein-github-actions is a Kotlin Multiplatform project that targets JavaScript only.
Each action is its own module and compiles to a single JS library file:

* `release-branches`
* `version-check`

[IMPORTANT]
====
*Development:* The Kotlin/JS actions run from their committed `dist/` directory, which `./gradlew bundle` builds.
A git hook rebuilds and stages it when a commit touches what goes into a bundle; enable it once per clone:

[source,sh]
----
git config core.hooksPath .githooks
----

CI fails if a committed `dist/` is stale, which also catches commits made with `--no-verify`.
====

Two more actions are composite actions, written in YAML only, with nothing to build:

* `gradle-kotlin-setup`
* `publish`


== version-check

Checks that the release being created, the Gradle version and the Antora documentation agree.
It fails the job, with one annotation per problem, unless:

* the release name is `\{Major}.\{Minor}.\{Patch}`, optionally followed by `-\{Tag}`;
* the tag of the release is the release name prefixed by `v`, such as `v1.2.3` for release `1.2.3`;
* when the Gradle check is enabled, which it is unless `check-gradle` is `false`:
** the root project and all the other projects of the Gradle build have the release name as their version;
* when `doc/antora.yml` exists:
** `version` is the release's version, `\{Major}.\{Minor}.\{Patch}` followed by `-\{Tag}` for a pre-release;
** `display_version` is that version without its patch and tag, `\{Major}.\{Minor}`, and is quoted so that YAML does not read `3.10` as the number `3.1`;
** the `version` attribute of `asciidoc.attributes` is the release's version;
** each `XXX-version` attribute of `asciidoc.attributes` equals the `XXX` version of the `gradle/libs.versions.toml` version catalog.

[source,yaml]
----
- uses: actions/checkout@v7
- uses: KodeinKoders/kodein-github-actions/version-check@v0.1
  with:
    release-name: ${{ github.event.release.name }}
----

The `tag-name` input defaults to `github.event.release.tag_name`, which is the tag of the release on a `release` event.

The Gradle check runs a Gradle init script on the build, with the `./gradlew` wrapper at the root of the repository, so the job needs a JDK (see `gradle-kotlin-setup`).
The script is written for the time of the run, in the path of the build, as `kodein_initScript_checkVersion.init.gradle.kts`.
It registers a task that fails if the version of the root project, or of any other project, is not the release name.
The command is `./gradlew --no-configuration-cache --no-daemon -I kodein_initScript_checkVersion.init.gradle.kts -PexpectedVersion=<release name> kodein_initScript_checkVersion -q`, and the check passes if it succeeds.

The Gradle build is expected at the root of the repository.
Set `gradle-build-path` when the build to check is not the root one, as for a multi-build Gradle project, where the root build includes several builds with `includeBuild` and only one of them is to be checked.
The wrapper is still the one at the root of the repository: `-p <gradle-build-path>` is added to the command, and the init script is written in that path.
The path is also used when `check-gradle` is `false`, for the `gradle/libs.versions.toml` version catalog read to check the Antora documentation.

[source,yaml]
----
- uses: KodeinKoders/kodein-github-actions/version-check@v0.1
  with:
    release-name: ${{ github.event.release.name }}
    gradle-build-path: mockmp
----

The action runs from `version-check/dist/`, which is committed.
Rebuild it after any change to the module with `./gradlew :version-check:bundle`.


== release-branches

Keeps a `release/v\{Major}.\{Minor}` branch on the commit of the latest release of that line.
With the `skip-release-prefix` input set to `true`, the branch is `v\{Major}.\{Minor}`, without the `release/` prefix.
For a release named `\{Major}.\{Minor}.\{Patch}`:

* if the branch does not exist, it is created at the release's commit;
* if it exists, it is hard reset to the release's commit.

A release with a `-\{Tag}` is a pre-release: nothing is done, and the action succeeds.
A release name that is not `\{Major}.\{Minor}.\{Patch}`, optionally followed by `-\{Tag}`, fails the action.

The branch is updated through the GitHub API, so no checkout is needed.
The job needs the `contents: write` permission.

[source,yaml]
----
permissions:
  contents: write
steps:
  - uses: KodeinKoders/kodein-github-actions/release-branches@v0.1
    with:
      release-name: ${{ github.event.release.name }}
----

The `commit` input defaults to `github.sha`, which is the commit of the release's tag on a `release` event.
The `token` input defaults to `github.token`.
The `skip-release-prefix` input defaults to `false`: for release `1.2.3`, the branch is `release/v1.2`, or `v1.2` when it is `true`.


== gradle-kotlin-setup

Prepares a runner to build a Gradle Kotlin project.
It:

* checks out the repository;
* installs a Temurin JDK;
* sets up Gradle, through `gradle/actions/setup-gradle`;
* caches `~/.konan`, unless Konan is disabled.

The Konan cache key depends on the runner's OS, on `gradle/libs.versions.toml` and on the Gradle build scripts.

[source,yaml]
----
- uses: KodeinKoders/kodein-github-actions/gradle-kotlin-setup@v0.1
  with:
    java-version: '21'
----

[cols="1,1,3"]
|===
| Input | Default | Description

| `java-version`
| `17`
| Version of the JVM SDK to install.

| `konan`
| `true`
| Whether to cache Konan, Kotlin/Native's toolchain.
|===

There is no need for a separate `actions/checkout` step.


== publish

Publishes the project to Maven Central and, for Gradle plugins, to the Gradle Plugin Portal.
It runs the Gradle wrapper, so the repository must be checked out and a JDK installed first, which `gradle-kotlin-setup` does.

* *Maven Central*: runs `publishAndReleaseToMavenCentral`, with signing enabled.
* *Gradle Plugin Portal*: runs `publishPlugins`, with signing enabled.

A step is skipped when one of its inputs is empty:

* the Maven Central step needs `central-portal-token-username`, `central-portal-token-password`, `pgp-signing-key` and `pgp-signing-password`;
* the Gradle Plugin Portal step needs `pgp-signing-key`, `pgp-signing-password`, `gradle-publish-key` and `gradle-publish-secret`.

A project without Gradle plugins therefore leaves the two `gradle-publish-*` inputs out, and a project that only publishes plugins leaves the two `central-portal-token-*` inputs out.
If both steps are skipped, nothing is published and the action fails.

[source,yaml]
----
- uses: KodeinKoders/kodein-github-actions/gradle-kotlin-setup@v0.1
- uses: KodeinKoders/kodein-github-actions/publish@v0.1
  with:
    central-portal-token-username: ${{ secrets.CENTRAL_PORTAL_TOKEN_USERNAME }}
    central-portal-token-password: ${{ secrets.CENTRAL_PORTAL_TOKEN_PASSWORD }}
    pgp-signing-key: ${{ secrets.PGP_SIGNING_KEY }}
    pgp-signing-password: ${{ secrets.PGP_SIGNING_PASSWORD }}
    gradle-publish-key: ${{ secrets.GRADLE_PUBLISH_KEY }}
    gradle-publish-secret: ${{ secrets.GRADLE_PUBLISH_SECRET }}
----

A composite action cannot read the `secrets` context, so the secrets are passed as inputs.

[cols="1,1,3"]
|===
| Input | Default | Description

| `central-portal-token-username`
| Empty
| The Maven Central Portal token username, to publish to Maven Central.

| `central-portal-token-password`
| Empty
| The Maven Central Portal token password, to publish to Maven Central.

| `pgp-signing-key`
| Empty
| The in-memory PGP key that signs the publications, for both targets.

| `pgp-signing-password`
| Empty
| The password of the PGP signing key, for both targets.

| `gradle-publish-key`
| Empty
| The Gradle Plugin Portal key, to publish plugins.

| `gradle-publish-secret`
| Empty
| The Gradle Plugin Portal secret, to publish plugins.

| `project`
| Empty
| The Gradle project to publish, such as `:lib`: the tasks are run as `:lib:publishAndReleaseToMavenCentral`.
Empty runs them without a project, `publishAndReleaseToMavenCentral`, which Gradle runs on every project of the build that has the task, not only the root project.
|===

A missing input arrives empty, and the step that needs it is skipped.
